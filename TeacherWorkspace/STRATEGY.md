# XQ Lesson Lab and the Big Bets

*A response to the product sync of August 6, 2026 and the "Big Bets" doc. Written
against the app as it exists on disk today (v1.0.3 shipped, v1.0.4 built and
pending release), with file references so every claim can be checked.*

## TL;DR

The Big Bets ask XQ to become open infrastructure under the systems schools
already run — and name **competency tools and mastery scanners** as the product
team's highest priorities. XQ Lesson Lab is already a working, shipped
embodiment of the two bets those priorities come from:

- **Bet 3 (Mastery in Place)** describes software schools run on their own
  systems, where no student data leaves and the school chooses its own AI
  model. That is this app's architecture, verified rather than promised.
- **Bet 1 (Competency DNA)** needs the framework to be *teachable and
  assessable*, not a poster. The app ships the XQ framework and places real
  student work on its progressions today.

And the "dev tools for teachers" philosophy from the sync — reviewable,
defensible, workflow-based, customizable, understandable — is not an
aspiration for this codebase; it is its existing design language, with
mechanisms to point at for each principle.

The proposal: treat Lesson Lab as the product team's vehicle for the two
highest-priority bets. Ship what's finished, then build the mastery scanner as
a batch extension of Skill Check, then close the loop between local Portraits
and the XQ framework.

## Where the app already sits, bet by bet

### Bet 1 — Competency DNA Layer

**Already in the app:**

- The full XQ competency framework, vendored from `xq-labs/xq-competencies`
  v1.1.0 into `Resources/XQFramework/`: 5 learner outcomes, 13 domains, 37
  competencies, 115 component skills, each skill with a 4-rung progression
  (emerging → developing → proficient → applying), CC BY 4.0 with attribution
  rendered on every screen and export that shows it.
- **Skill Check** places a piece of student work on a component skill's
  progression (`SkillCheckView.swift`, `EvaluationPipeline.swift`). This is the
  "implement teaching and assessment against the DNA" half of the bet, working
  today on a 2B on-device model.
- The framework loader reads rung labels from the CSV headers rather than
  hardcoding them (`XQFramework.swift`), so the bet's "adding or splitting
  competencies where needed" is a data update here, not a rewrite.

**The gap:** the app has *two* competency models that don't touch. Skill Check
uses the real framework; the Portrait of a Graduate artifact is a hardcoded
5-competency list in the system prompt (`AppState.systemPrompt`), generated by
the local model with no connection to the CSVs. The bet's core loop —
**decompose** a local Portrait into the shared DNA, **implement** against it,
**recompose** evidence back into the local Portrait — is exactly the bridge
between these two halves. Both ends exist; the middle doesn't yet.

### Bet 2 — Meaningful Engaged Learning

**Already in the app:** teachers improve *existing* materials in chat every
day — attach a lesson (PDF/docx, extracted on-device), ask for a revision, get
an editable artifact back. That's the bet's spirit, unindexed.

**The gap:** no dedicated "lesson lift" workflow, and improvements aren't
indexed to DNA progressions. Once the MEL design principles are codified
(the memo referenced in the bets doc), they could ship the way the XQ
framework did: as curated data the model applies, not model knowledge — the
same principle that kept standards alignment out of the app until a curated
NGSS dataset exists (`ROADMAP.md`, Phase 3).

### Bet 3 — Mastery in Place

This bet reads like a description of the app's architecture:

| The bet says | The app does |
|---|---|
| "Schools install and run on their own systems" | Native macOS app, model runs in-process (llama.cpp, Metal), works offline |
| "No student data leaves the school — including to XQ" | No telemetry; rosters, notes, chats, and student work never leave. The one opt-in network path (second opinions) excludes student work entirely and is gated by a deterministic redaction check — a `ReviewPayload` that would leak a roster name cannot be constructed (`ReviewPayload.swift`), and `scripts/check-no-pii-leaves.sh` verifies it as a release gate |
| "Schools choose their own AI model: any cloud LLM, or a fully local one" | 8-model catalog (`ModelCatalog.swift`), download/switch/delete in-app; cloud only as an explicit per-document second opinion |
| "A mastery layer that analyzes existing assignments and maps them to standards and competencies" | Skill Check does this for **one** work sample at a time — the scanner is the batch version, and most of its pieces already exist |
| "AI assessment with human-reviewable reasoning" (from the sync) | Evidence is a sentence *index* into the student's own text, so a fabricated quote isn't representable; the teacher can move any placement and the model's original is preserved beside it |

**The gap:** batch. A scanner needs to ingest a *set* of submissions (folder
of files first — Google Classroom is an org blocker, see Asks) and present a
class-level view where every cell is an individually reviewable Skill Check.
Also: the bet says **open-source**, which is a decision this repo hasn't made.

### Bet 4 — One Evaluation Framework

The app's honest role is small but real: it generates exactly the kind of
school-level, non-vanity evidence the framework's **self-service tier**
describes — placements, teacher overrides, and an append-only audit trail
(`FrontierAuditLog.swift` for network events; `SkillEvaluation` snapshots for
placements). When the unified framework exists, an evidence export from the
app could be one of its open, third-party-verifiable instruments. Nothing to
build until the framework is defined.

### Bet 5 — Solutions Architecture

The app is a thing solutions architects deploy, and the repo is unusually
ready for that: ~40 headless probes (`App.swift`), documented release gates,
a test kit with green-status fixtures (`TestData/skill-check/README.md`), and
an audit log "a principal or a district privacy officer can read." The
implementation guidance the bet calls for could be extracted largely from
what's already written down here.

## The philosophy bar, met with shipped mechanisms

The sync set the bar at: *even anti-AI-in-schools activists should find these
tools acceptable.* Principle by principle, what the app already does:

| Principle | Shipped mechanism | Where |
|---|---|---|
| **Reviewable** | Consent sheet shows the literal bytes before anything sends; teacher can edit them and the redaction gate re-runs on the edit. Every send *and every block* is appended to an audit log that carries the full verbatim payload — "an audit log that summarises what it sent is not one" | `FrontierReviewSheet.swift`, `FrontierAuditLog.swift` |
| **Rollback-able** | The teacher can move any placement; the model's number is never overwritten, and the UI says "You moved this from *Developing*." Nothing auto-writes to a teacher's document — review actions are copy or jump-to-editor only | `SkillEvaluation.teacherLevel` / `effectiveLevel`, `ReviewCard.swift` |
| **Defensible** | A placement always shows the descriptor it matched and the student's own quoted sentences. Quotes are sentence indexes into the app's own copy of the text, so the model *cannot* fabricate evidence — the worst it can do is point at the wrong real sentence, which a teacher can see | `EvaluationPipeline.swift`, `WorkDocument.swift` |
| **Workflow-based** | Evaluation is staged small calls reconciled deterministically in Swift, with live progress ("Testing Proficient"), hedges surfaced not hidden ("mixed evidence", off-topic), and a footer that says "A draft judgment — you decide." | `EvaluationPipeline.swift`, `SkillCheckView.swift` |
| **Customizable** | My Classroom *is* the "ClaudeMD for teachers": structured context (classes, rosters, notes, subject) that drives every generation, plus @mentions to pull specific context inline | `ClassroomView.swift`, `Mentions.swift` |
| **Understandable** | Every automated step is something a teacher could have done by hand: read one rung, ask "does the work meet this?", cite a sentence. De-identification is a deterministic token list built from the teacher's own roster, not a model guess — explainable to a privacy officer in one paragraph | `Deidentifier.swift`, `PIILexicon.swift` |

This is the strongest card the product team holds: the philosophy from the
sync doesn't need to be piloted. It's running.

## Recommended sequence

*(A recommendation, not a decision — ordering below is mine.)*

1. **Now — ship v1.0.4.** Second opinions is feature-complete, probe-covered,
   and sitting uncommitted, along with the positioning shift from "nothing
   leaves your Mac" to "nothing leaves without your say-so." Shipping it also
   ships the audit/consent machinery every later cloud-assisted feature will
   reuse.
2. **Next — Mastery scanning MVP (Bet 3, the sync's top priority).** Batch
   Skill Check across one assignment's submissions: ingest a folder of files,
   run the existing pipeline per submission, present a per-skill class view
   where each cell opens the same reviewable, overridable single-sample UI.
   Starting with file import means the org's OAuth timeline doesn't gate the
   product proof. Detail in `ROADMAP.md` Phase 5.
3. **Then — Portrait decomposition (Bet 1).** Connect the two competency
   models: map a school's local Portrait competencies onto XQ component
   skills, and recompose Skill Check / scanner evidence into the Portrait
   view. This turns the scanner's output into the bet's recompose step.
   Detail in `ROADMAP.md` Phase 6.
4. **Later** — MEL "lesson lift" workflow once the codified principles exist
   (Bet 2); evidence export once the unified evaluation framework is defined
   (Bet 4).

## Asks of the organization

Ordered by how directly they block the sequence above:

1. **Google Classroom OAuth client / GCP project.** The single blocker between
   "mastery scanner on a folder of files" and "mastery scanner on the
   teacher's actual assignment stream." Engineering-ready on this side
   (`ROADMAP.md` Phase 2 has carried it since July).
2. **Open-sourcing decision.** Bet 3 says "open-source software" explicitly.
   The repo's trust story is strongest if the redaction gate and evaluation
   pipeline are inspectable by the districts we're asking to trust them.
3. **XQ-hosted proxy for second opinions.** BYO Anthropic key is a real
   adoption barrier for teachers. The `.hosted` credential path is designed
   and scaffolded (`FrontierProvider.swift`) — consent, redaction, and audit
   all sit above the transport, so this is a service + one copy string, not a
   rework.
4. **Framework refinement cadence (Bet 1).** Changes to competencies land here
   as a vendored data update; the app already tolerates rung-count changes.
   What it needs from the framework team is versioned releases on a known
   cadence, which `Resources/XQFramework/VERSION` is already built around.
